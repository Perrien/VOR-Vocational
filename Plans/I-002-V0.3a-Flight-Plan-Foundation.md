# I-002 V0.3a — Flight-plan foundation

**Idea:** I-002 — First supplied mission: Silverkeep to Midland  
**Status:** In progress; work item 1 is complete and verified
**Goal:** Make the authored Silverkeep Strip → Midland Cityport route a bundled, validated data input and derive its geometry, distances, still-air estimate, and player-readable VOR guidance without adding Mission UI.

## Outcome

V0.3a ends with pure, automated flight-plan behavior. The app can decode the
supplied route, resolve its airport and VOR references against the fixed Myosia
world, calculate its route, and create the data that V0.3b will display in a
briefing and read-only Flight Plan panel.

There is deliberately no Transport entry, planner screen, route overlay,
mission flight wrapper, arrival action, elapsed-flight clock, score, wind, or
debrief in this plan.

## Plan-data decision

The bundled JSON stores authored facts only: plan identity, title, origin,
ordered waypoints, destination, and the existing terminal ELS radial
reference. It
does **not** store precomputed intersection coordinates, bearings, leg
distances, total distance, or ETA.

The resolver calculates all derived values from the JSON plus bundled world
data. It receives cruise speed as an input rather than baking the current
`FlightSession` default into the plan. V0.3a's canonical test uses 260 kt;
V0.3b can present that as the supplied planning speed without treating an
in-flight speed change as a scoring rule.

The terminal MFD R-078 / ELS R-353 intersection resolves about 0.18 NM from
Midland. That is the practical plotted fix available from whole-degree OBS
settings and a chart without exact airport coordinates; rounded radial values
therefore do not form a literal final ELS-353 line segment to the airport.
Model ELS R-353 as an explicit terminal **player reference**, not a normal
tracking leg and not a reason to modify Myosia coordinates. In V0.3c, the
player chooses “Flight Complete”; the app records the aircraft's actual
position at that moment and reports its distance from Midland. It does not
auto-detect arrival or apply an arrival radius in V0.3.

## Data and domain shape

Create the following small, pure domain boundary:

```text
FlightPlan (Codable input)
  id, name
  origin: PlanPoint
  waypoints: [PlanPoint]
  destination: PlanPoint
  terminalReference: RadialReference?

PlanPoint
  airport(ICAO)
  vor(stationID)
  intersection([two RadialReference values])

ResolvedFlightPlan (derived output)
  resolved ordered points and normalized coordinates
  ordinary FlightPlanLeg values: geometry, distance, guidance
  optional terminal-reference guidance
  total distance and still-air estimate
```

`FlightPlanResolver` accepts a `FlightPlan`, `[Airport]`, `[VORStation]`, map
dimensions, and cruise speed. It reports a typed, readable validation failure
for malformed references, duplicate intersection stations, no usable radial
intersection, out-of-chart/receiver-range fixes, coincident consecutive
points, non-finite calculations, and an invalid terminal-reference.
Keep SwiftUI and `Bundle` access outside this resolver so the navigation math
can be tested with small world fixtures.

Use the existing player-facing guidance wording as the expected output:

1. Silverkeep → Mossbarrow: MSB 117.15, OBS 103, TO.
2. Depart Mossbarrow: MSB 117.15, OBS 154, FROM.
3. First fix → Marrowfield: MFD 116.25, OBS 106, TO.
4. Depart Marrowfield: MFD 116.25, OBS 078, FROM.
5. Terminal position reference: ELS 112.00, OBS 353, FROM; use it to locate
   Midland before choosing Flight Complete.

The normal legs' courses are derived from their point semantics and geometry.
The JSON's terminal reference disambiguates the final instructional
radial while preserving the canonical airport destination geometry.

## Explicit boundaries

- No mission-list activation or `AppDestination` changes.
- No SwiftUI briefing, Flight Plan panel, chart route overlay, chart-aid
  policy, or Mission-specific `FlightSurfaceConfiguration` preset. Those are
  V0.3b decisions.
- No `FlightSession` elapsed-time state, active-leg selection, automatic
  transitions, arrival marking, result screen, tracking, scoring, wind, or
  debrief. Those are V0.3c or I-003.
- No player-authored plans, persistence, arbitrary map points, DME arcs,
  aircraft model, terrain, or iPad work.
- Do not update dependencies, signing/capabilities, entitlements, bundle ID,
  or the Xcode project file.

## Stop conditions

Stop and ask before proceeding if any of these is true:

- The actual authored route cannot resolve with the fixed Myosia data or an
  intersection is outside the required service range.
- A plan requires arbitrary coordinates, a third radial, a scoring rule, or
  automatic arrival detection before V0.3c, rather than the bounded terminal
  reference representation above.
- A package/dependency, Xcode-project edit, or change to bundled world data is
  required to load the JSON.
- A test outside this scope fails, or existing uncommitted work overlaps a
  named file.
