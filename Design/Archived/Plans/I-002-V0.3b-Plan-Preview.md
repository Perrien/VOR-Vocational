# I-002 V0.3b — Plan preview

**Idea:** I-002 — First supplied mission: Silverkeep to Midland  
**Status:** Complete  
**Goal:** Let a player open the Transport mission and inspect the supplied Silverkeep-to-Midland plan as a read-only chart preview and Flight Plan briefing, without starting or simulating a mission flight.

## Outcome

V0.3b makes the already-validated bundled plan visible. From Home → Missions,
Transport becomes the one actionable catalog entry. Its briefing presents the
route on a static Myosia chart, the planned distance and still-air estimate,
and the five VOR actions a player will later use in flight.

This is a preflight reference, not a mission flight. It deliberately has no
aircraft marker, cockpit, live NAV readings, play controls, active-leg state,
or Flight Complete button. The full route is allowed on this briefing chart;
that does not authorize revealing the route or true position during V0.3c
mission play.

## Current context

- V0.3a bundled `SilverkeepToMidland.json`, validates it with
  `FlightPlanResolver`, and supplies `ResolvedFlightPlan`: six points, five
  geometry legs, four ordinary VOR-guidance legs, and one separate ELS R-353
  terminal reference. The route is 99.18 NM and takes about 22.89 minutes at
  the fixed planning speed of 260 kt.
- The final MFD R-078 / ELS R-353 intersection is a practical plotted
  reference roughly 0.18 NM from Midland, not the literal airport coordinate.
  The plan panel must therefore render ELS 112.00 / OBS 353 / FROM as a
  **Final position reference**, rather than inventing a fifth guided geometry
  leg or an arrival rule.
- `MissionsListView` currently delegates every entry to the non-interactive
  `ModeListView`. `PracticeListView` demonstrates the appropriate local-state
  pattern for one actionable catalog row without changing `AppDestination`.
- `MapView` owns a live `FlightSession`, plane marker, cockpit, chart controls,
  and simulation. Reusing it for this preview would imply live-flight behavior
  and a visible true position. The preview instead composes the existing
  `FlatMap` artwork and crop projection directly with a route-only overlay.
- `FlatMap.point(for:in:)` is the authoritative conversion from bundled
  normalized coordinates to the cropped chart. Route drawing must use it, so
  the plan stays aligned with the map at every window size.
- The app target defaults declarations to `MainActor`. Any new pure briefing
  value types must be explicitly `nonisolated`; SwiftUI views stay on the main
  actor.

## Presentation decision

Build a small immutable `FlightPlanBriefing` from `ResolvedFlightPlan` before
SwiftUI renders anything. It contains the plan summary and five actionable
items: the four ordinary guided legs plus the separate terminal reference.
Normal items retain their calculated leg distance and semantic
`VORGuidance`; the terminal item has no fabricated distance or airport leg.
Formatting (for example, `MSB 117.15 · OBS 103 · TO`) belongs in the view.

The Transport briefing screen uses a fixed, full-route chart alongside a
scrollable read-only Flight Plan panel. The chart uses a distinct planned-route
stroke and named point markers for the start, both VORs, the two fixes, and
Midland. The briefing panel presents the five navigation actions in order, so
a player can connect each instruction to its location on the chart.

If the bundled plan cannot be read or resolved, the screen must say that the
Transport briefing is unavailable and show the validation message plus a Back
to Missions control. It must not crash or silently show an empty plan.

## Explicit boundaries

- No `AppDestination` expansion, navigation stack, persistence, plan picker,
  user-authored route, or second supplied route.
- No `MapView`, `FlightSession`, `FlightSurfaceConfiguration`, cockpit,
  aircraft spawn, live NAV reading, timer, active-leg selection, automatic
  transition, or simulated movement change.
- No Start Flight, Flight Complete, elapsed-time display, arrival radius,
  result, scoring, wind, path recording, debrief, or mission-specific chart
  aid policy. Those belong to V0.3c or I-003.
- No changing Myosia JSON, route coordinates/radials, test tolerances,
  dependencies, signing/capabilities, entitlements, bundle ID, or the Xcode
  project file.

## Stop conditions

Stop and ask before proceeding if any of these is true:

- The chart crop cannot show any resolved plan point or route line accurately
  without changing fixed Myosia data or the core coordinate conversion.
- Making the preview visible requires putting planned geometry or true aircraft
  position into the live Mission flight surface, rather than a dedicated static
  briefing chart.
- The resolved plan has no terminal reference, more/fewer than the expected
  player actions, or a new instruction shape that needs a product decision.
- A package, Xcode-project edit, new app target, or unrelated test failure is
  required.
