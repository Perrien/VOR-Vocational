# I-002 V0.3c — Transport mission loop

**Idea:** I-002 — First supplied mission: Silverkeep to Midland  
**Status:** Complete  
**Goal:** Let the player launch the supplied Transport briefing into a live, instrument-led flight from Silverkeep, follow its active VOR instructions, mark Flight Complete when they judge they have reached Midland, and receive their simulated elapsed time plus exact distance from Midland.

## Outcome

V0.3c completes the first playable supplied-mission loop:

```text
Home → Missions → Transport briefing → Fly Transport → Flight Complete → result
```

The flight begins at Silverkeep Strip and reuses the current chart, heading
controls, NAV radios, aircraft simulation, and playback controls. It adds a
small mission card with the current instruction, elapsed **simulated** time,
manual instruction advancement, and a Flight Complete action. The active
instruction begins at the first of the briefing's five actions; the player
presses Next instruction when they decide to move on. This is intentional:
automatic fix recognition would require new location tolerances and would make
the mission silently evaluate the aircraft's true position.

The live mission chart must not display the planned route or the aircraft icon.
The aircraft still has an exact internal position so its NAV indications and
movement work normally. When the player presses Flight Complete, movement
pauses and the app records that exact position, calculates its direct distance
to Midland Cityport, and presents it alongside simulated elapsed time. There is
no automatic arrival, arrival radius, pass/fail threshold, route score, or
debrief in this slice.

## Current context and decisions

- V0.3a supplies the validated `SilverkeepToMidland.json` and an immutable
  `ResolvedFlightPlan`: six points, four normal VOR-guided legs, one
  chart-only final intersection-to-airport geometry segment, and a separate
  ELS R-353 terminal position reference. The final plotted intersection is
  approximately 0.18 NM from Midland; it is deliberately not an exact airport
  coordinate or an arrival rule.
- V0.3b supplies `FlightPlanBriefing`, the static `TransportBriefingView`, and
  the player-visible five action rows. The briefing already owns the resolved
  plan content, so it can pass that same immutable content to the mission view
  instead of loading a potentially different plan again.
- `FlightSession` owns mutable aircraft position, heading, speed, playback,
  radios, camera, and chart preferences. It currently has no elapsed-time
  field. `MapView`'s private `FlightTimerView` advances the session by wall
  time multiplied by `timeMultiplier`; V0.3c must record that same multiplied
  duration as simulated time.
- `FlightSurfaceConfiguration` gives each mode a named surface policy.
  V0.3c adds a `transportMission` policy: simulation and the normal cockpit
  flight controls remain available; airports begin visible; sightseeing names
  begin hidden; the aircraft marker is not rendered and therefore cannot be
  dragged. The normal Chart controls remain available, but no route layer or
  true-position aid is added.
- The retired planning note in `Design/Documents/FlightPlanning.md` describes
  an arrival area and route-tracking score. That conflicts with the later
  V0.3a decision and the owner's stated behavior: Flight Complete is user
  selected and reports distance from the literal airport. This plan follows
  the current IDEA, archived V0.3a plan, and that decision; scoring and
  tolerances remain I-003 work.
- The app target defaults declarations to `MainActor`. New immutable progress
  and completion values must be explicitly `nonisolated`; `FlightSession` and
  SwiftUI views remain main-actor-owned.

- Define an explicitly `nonisolated`, Equatable `MissionFlightProgress` for an

## Explicit boundaries

- No route tracking, track recording, wind, ETA scoring, arrival radius,
  grade, pass/fail state, debrief, or persistent mission history. I-003 owns
  mission quality and debrief design.
- No automatic leg transitions, location checks for instruction progress,
  radio/OBS auto-configuration, GPS coordinate display, plane marker, or
  planned route layer in the live mission.
- No user-authored plans, plan picker, second supplied mission, terrain,
  aircraft-performance model, iPad target, dependencies, signing/capability
  changes, entitlements, bundle-ID changes, or Xcode-project edits.
- No edits to the Myosia world, supplied route JSON, radial values,
  intersection tolerance, or existing test tolerances merely to make the
  mission appear easier to complete.

## Stop conditions

Stop and ask before proceeding if any of these is true:

- Hiding the aircraft marker also prevents the existing NAV radios or flight
  simulator from receiving the actual aircraft position.
- The supplied plan cannot provide exactly the expected four normal actions
  plus one terminal reference, or a new instruction shape needs a product
  decision.
- Accurate elapsed simulated time cannot be collected at the same time and
  multiplier used for movement without redesigning the existing simulation
  loop.
- A result would need an arrival tolerance, score, route-tracking sample, or
  new world-data field before it can report raw distance from Midland.
- A package, Xcode-project change, unrelated failing test, or change to fixed
  Myosia data is required.
